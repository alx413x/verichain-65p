VeriChain Passport 产品需求说明
# 1. 需求背景
高价值消费电子产品（如智能手表、奢侈手机）在生产、流通、保修、二次交易过程中，存在造假、保修欺诈、服务定责不清等痛点。传统系统各方（制造商、服务中心、消费者）信息壁垒严重，真假难验、责任难查，二手市场信息不透明、信任基础薄弱。
VeriChain Passport 基于以太坊智能合约，面向行业全链路提供：
- 制造溯源唯一数字认证、防伪验真；
- 产品所有权全周期流转登记、不可篡改；
- 用户申请保修、维修中心验证全流程链上存证，可自动失效、自动仲裁。
核心价值：为制造商树立公信力、消费者获得透明权益保护、服务中心规范履责，极大提升产业链协同效率。

# 3. 四方用户旅程（User Journey）
## 3.1 用戶認證
- 通过绑定用户的区块链钱包完成身份认证与权限识别，系统以钱包地址作为用户身份标识，并据此分配角色与访问权限（例如 Manufacturer、Retailer、ServiceCenter、Consumer、Admin）。
- 用于所有与链上操作相关的 DApp 前端与后台权限控制
- 主要流程（成功场景）
    1. 用户点击“连接钱包”按钮；
    2. 前端调用钱包 API 请求连接（requestAccounts）；
    3. 钱包弹窗请求用户授权连接并返回用户地址（address）；
    4. 前端展示已连接状态（地址缩写显示，如 0x1234...abcd）；
- MetaMask 交互觸發

## 3.2 产品查詢
- 用戶输入 productId，前端调用合约读取产品信息与历史事件（ProductRegistered、OwnershipTransferred、ServiceRecorded），并显示制造商、序列号、当前所有者、保修起止、剩余索赔次数及维修历史。

## 3.3 制造商 （`AccessControl` needed）
- 登录Dapp后台，创建新产品唯一电子护照，录入序列号、型号、制造时间等，发布上链。
- 产品发往零售商，系统自动登记所有权转移（制造商→零售商）。
- 可随时查询所有自身销售产品的状态、已转手记录、保修服务信息。
- 主要流程（成功场景）
    1. 制造商通过钱包 (base on the user address)，系统确认其制造商角色权限（链上访问控制）。
    2. 在“创建产品”表单中录入：序列号、型号、初始保修开始时间与期限（duration）、最大允许索赔次数。(頁面2)
    3. 系统对关键信息做客户端校验（格式、必填项、序列号唯一性检查）。然后在首页（页面1）显示新产品。
    4. 制造商选择接收零售商地址并提交，並且進行簽署。智能合约记录事件。(頁面3) 然后在首页（页面1）显示产品状态。
    5. 出货后，制造商可在其后台查看所有已注册商品的状态 (Sold/ In Stock)记录与对应保修信息。
        - 异常与边界情形
            - 重复序列号：合约应拒绝注册并返回错误（DuplicateSerial）。
            - 未授权账户调用(check sign value)：合约拒绝并返回 Unauthorized。
            - 出货指定零售商不存在或未注册：拒绝或转为待登记状态并通知管理员。
## 3.4 服务中心（`AccessControl` needed）
- 登录Dapp，验证用户提交的产品ID、所有权、保修有效期与索赔次数等信息。
- 审核保修请求：匹配产品历史，合规即可链上登记维修记录。
- 完成服务后，更新维修详情、状态和新的保修信息上链。
- 可查看所有已服务产品的历史与当前状态，掌握责任归属、杜绝虚假保修。
    - 主要流程（成功场景
        1. 读取链上产品信息（Product Serial Number/ Customer Address/ Status/ Date 。并列出所有待处理的保修申请。用户可以点击“查看详情”以获取更多信息。（頁面1） 
        2. 服务中心（system）核对申请人身份与当前所有者，并验证保修仍在有效期且索赔次数未超限。
        3. 对合规请求，服务中心在链上调用 approveClaim 函数，写入维修记录，并更新 claimCount 或剩余保修。（頁面2）
        4. 对拒绝的请求，服务中心调用 rejectClaim 并写入拒绝理由与证据哈希，触发 ClaimRejected 事件。（頁面2）
        A rejection reason should be uploaded by the staff of customer service center as record for claim
        5. 完成维修流程后，服务中心在链上更新服务结果（例如 Repaired/ Reject），并触发 ServiceRecorded 事件(sign by staff)，客户和制造商可接收通知。(status display on 頁面1)
            - 保修已过期或索赔次数已满：应拒绝并记录拒绝原因。
            - 服务中心误操作或恶意记录：系统应保留变更记录（不可篡改），并允许管理员发起争议处理与人工仲裁流程。

## 3.5 消费者（`AccessControl` needed）
- 通过Dapp前端输入/扫描产品ID，查询产品来源、历史流转记录与保修状态，核验真伪。
- 购买产品后，系统更新所有权至本人账户（可通过钱包、手机号或邮箱认证）。
- 保修到期或需要售后维修时，在线提交保修申请，系统实时反馈进度与审批结果。
- 二次转售时，发起所有权转移，新买家可全程验证链上历史，保障权益。
- 主要流程（成功场景）

1. 产品列表（我的数字护照） （頁面1）
    - 页面展示当前用户拥有的所有产品，用户可以对每个产品进行操作，包括提交保修申请和转让所有权。s

2. 提交保修请求： （頁面2）
    - 若出现问题，消费者在前端填写申请表并上传证据（文字/照片/视频），提交后合约或后端创建 claim 记录并触发 ClaimSubmitted 事件。
    Input field for the user to explain the claim

3. 二次转售： （頁面3）
    - 消费者在转售时发起 OwnershipTransfer 给买家

## 3.6 零售商（`AccessControl` needed）
- 通过 DApp 后台或关联钱包地址登录，具备零售商角色权限（由制造商或系统管理员授予/注册）。
- 登录后可查看待接收的发货产品列表、库存、在售产品及已售出的历史记录。
主要用例（成功流程）

1. 查看待接收与库存 （頁面1）

    - 系统展示待接收发货列表（基于链上 TransferPending 或 OwnershipTransferred 事件与后台索引），以及当前库存、在售与已售记录。

2. 产品注册
    - 零售商门户可以将产品上传至产品库存列表。


3. 销售与所有权转移（零售商 → 客户） 
    - 将 currentOwner 设置为 buyerAddress。

# 5. 架构设计
1. 用户 (User)
    - 描述: 系统的参与者，根据其角色（制造商、零售商、消费者、服务中心）与前端应用进行交互。
    - 交互方式: 通过点击按钮、填写表单来触发业务逻辑。同时，他们也是钱包的最终控制者，负责批准或拒绝 MetaMask 弹出的签名请求。
2. 前端应用 (Frontend App)
    - 技术: React.js 或 Vue.js。
    - 职责:
    - UI/UX: 提供用户友好的界面，根据连接的钱包地址的角色，动态展示不同的门户（Dashboard）。
    - 状态管理: 管理应用的前端状态。
    - 构建交互: 使用 Ethers.js 库来构建与智能合约交互的请求。
3. Ethers.js (核心库)
    - 职责:
    - 读取数据 (Read): 格式化调用智能合约的 view 和 pure 函数的请求，用于从链上免费读取数据（如获取产品详情）。
    - 写入数据 (Write): 格式化调用状态变更函数的交易（如 mint 或 transfer）。
    - 事件监听 (Listen): 监听智能合约触发的事件，以便实时更新前端 UI。
4. MetaMask (钱包)
    - 职责:
    - 身份管理: 作为用户的数字身份凭证。前端通过它获取用户的钱包地址。
    - 安全网关: 拦截所有需要写入区块链的交易请求，以弹窗形式请求用户授权。
    - 交易签名: 使用用户存储在本地的私钥对交易进行签名，这是所有权和操作权限的根本保障。
5. RPC 节点 (RPC Node)
    - 服务: 如 Infura, Alchemy, 或本地的 Hardhat 节点。
    - 职责:
    - 区块链网关: 充当你的 dApp 与以太坊区块链之间的通信桥梁。
    - 广播交易: 将 MetaMask 签好名的交易广播到整个以太坊网络中，等待矿工打包。
    - 数据查询: 响应 Ethers.js 发来的数据读取请求，从区块链查询数据并返回。
6. 智能合约 (Smart Contract - ProductPassport.sol)
    - 技术: Solidity。
    - 职责:
    - 业务逻辑核心: 包含了所有关于产品注册、所有权转移、保修管理和角色控制的规则。
    - 状态管理: 负责在链上存储 (On-Chain Storage) 中创建、更新和删除数据。
    - 事件触发: 当关键业务发生时（如 Transfer 事件），会触发事件 (Events)，向外界广播状态变化。
